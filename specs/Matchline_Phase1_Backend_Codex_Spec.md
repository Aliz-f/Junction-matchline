# MATCHLINE — Phase 1 Backend Implementation Specification

**Document ID:** ML-BE-P1  
**Version:** 2.4 (end-to-end workflow and contract reconciliation) · 24 October 2026  
**Audience:** Backend engineer / OpenAI Codex agent  
**Product:** Matchline (working name)  
**Status:** Harmonized against frontend v2.4; implementation-ready with contract gates; external provider credentials and data rights remain external dependencies.

> **Critical product correction:** Post-match **What-if** is a multi-turn **user ↔ AI conversation**. The user proposes an alternative match event or coaching decision; AI examines the user's reasoning, identifies supporting/contradicting evidence, challenges assumptions, explains uncertainty, and responds to follow-up questions. This is not merely a user-to-user chat room, an automatic score predictor, or a one-shot generated answer. Community rooms are a *separate* feature. Phase 1 conversations remain private; explicitly consented excerpt sharing requires editor approval and belongs to Phase 2.

## 1. Decisions, outcomes, and implementation phases

### 1.1 Locked product decisions

1. Sport: English football. **Premier League is the Phase 1 primary league**; future competition adapters may add UEFA Champions League, FA Cup, EFL Cup, Europa League, and other leagues.
2. Main experience: an interactive, Candy Crush-inspired **Match Journey** of one match per node. Each node contains pre-match and post-match capabilities.
3. Journey node appearance: **competition determines primary color and motifs**; **match status determines icon, animation, and label**. Do not infer a competition from a hex color.
4. Separate geographical map: England stadiums with verified coordinates; upcoming-round, live, finished, inactive, postponed/cancelled are distinct states.
5. Favorite team personalizes Journey, map, impact, recommendations, and standings without hiding other teams.
6. Match/standings impact uses deterministic football rules. AI may explain those results but never supply arithmetic or invent evidence.
7. Free users can **read and contribute** to existing community rooms. Premium users can additionally **create rooms**. Role enforcement must be server-side.
8. Predictions are locked at kickoff. Checkable predictions are rule-scored; interpretive reasoning gets clearly distinct, non-objective feedback.
9. The platform labels verified facts, AI commentary, and hypothetical reasoning; AI conversations must report uncertain and insufficient evidence.
10. The developer interpretation API is a Phase 2 objective; Phase 1 must retain ownership/consent and provenance fields needed later.

### 1.2 Two-phase product implementation plan

| Capability | Phase 1 — functional, demo-ready vertical slice | Phase 2 — expansion / productionization |
|---|---|---|
| Sport/data | **Required:** Premier League-compatible provider-neutral models, verified curated venues and an explicitly labelled synthetic demo adapter. **Conditional P1 (not G0–G5 blocker):** external football-data.org adapter only after rights and credentials are confirmed. | Other English competitions, multi-league/sport adapters, richer data feeds |
| Journey + map | Match, venue, team, standings, state endpoints | Live push of match updates, cross-competition journey, advanced filters |
| Personalization | One favorite team; saved profile; guest browsing; **deterministic match recommendations from Journey and Impact** | Multi-team follows, ML/behavioral recommendations, notifications, richer analytics |
| Community | Pre-match and post-match rooms, free contributions, premium room creation, moderation basics | Scalable real-time rooms, reply threads, fan communities, discovery ranking |
| Predictions | Structured outcome and optional score prediction, lock at kickoff, deterministic scoring and basic badge | Natural-language claim extraction with user confirmation, complex claim types, calibration and disputes |
| Post-match What-if | **Multi-turn user ↔ AI conversations** with evidence, alternatives, fact references, safety validation but no sharing | Rich historical context, comparisons, group what-if sessions, long-running reasoning, export to creator ecosystem |
| Impact | Deterministic points gap / conditional standings scenarios, grounded explanation | Advanced multi-game scenarios, title/relegation projections, probability modeling with calibration |
| Identity/payments | Real basic login; seeded/demo premium role without payment gateway | Billing, subscription lifecycle, editor workflow, stronger fraud controls |
| Developer ecosystem | Record explicit consent/visibility, use internal typed representations | Authenticated, versioned interpretation API, webhooks, partner analytics, revocation |

**Phase 1 Definition of Done:** an authenticated user chooses an EPL club, explores its Journey and a match, checks impact on their team, contributes to a pre-match room, submits a prediction before cutoff, views its verified result after completion, opens a multi-turn What-if chat about a finished fixture, sees cited match facts and uncertainty, explores the stadium map. Phase 1 never publishes AI conversations or excerpts; sharing is Phase 2. The demo must work entirely with labeled synthetic fixture data without sports-data credentials; the **external football provider is optional P1** and never a prerequisite for G0–G5. The **working remote AI model adapter is required code**, with its G4 live smoke test BLOCKED rather than PASSED until credentials/network exist.

### 1.3 Explicit Phase 1 exclusions

Do not implement payment checkout, gambling/odds, automatic publication of private AI content, exact counterfactual score predictions, unrestricted free-text claim extraction, multi-sport scoring, ML betting tips, or third-party public API keys. Do not present synthetic fixtures as live or factual. Live minute-by-minute synchronization and horizontal WebSocket scaling are Phase 2 unless trivial with the chosen provider and quota.

## 2. Proposed backend stack and repository contract

- **Python** current supported 3.12+; **FastAPI** with Pydantic v2 request/response models.
- **PostgreSQL** 16+; **SQLAlchemy 2.x async**, **Alembic** migrations; `asyncpg` or compatible maintained driver.
- **httpx** for upstream API requests; `pytest` / `pytest-asyncio` / HTTPX test client; `ruff` and optional `mypy`.
- **Argon2id** password hashing; an opaque randomly generated session token in a secure HttpOnly cookie and a hashed copy stored in the database. Never use client-supplied role values as authority.
- **Redis is not required for Phase 1**. Use DB persistence and short-interval polling from the frontend; add Redis/pubsub and WebSockets in Phase 2 if scale requires. This minimizes deployment complexity.
- **AI model adapter** behind a service interface; model API key is backend-only. Implement **both** the explicitly labelled `DEMO_AI` scripted mock (for deterministic offline CI) **and a working configurable remote-model adapter in Phase 1** using `AI_BASE_URL`, `AI_MODEL`, and server-only `AI_API_KEY`. A real-model unscripted two-turn evidence-grounded smoke test is a **G4 acceptance requirement when credentials are provisioned**; if they are absent, G4 remote acceptance must be recorded as BLOCKED, never silently counted as passed. Only remote validated replies use `AI_ANALYSIS`.
- Docker Compose for `postgres` + `api`; `backend` runs as one service; provider sync is an explicit command or separate one-off scheduled job, never initiated by every FastAPI worker.
- **Contract-first:** Appendix A v2.4 remains authoritative **before and after** FastAPI publishes `/openapi.json`. OpenAPI must implement the frozen Appendix A schemas; frontend generates types **only from conforming OpenAPI**, and CI blocks any schema drift. Any change requires a matching PR/update in both specifications and both task lists before either agent proceeds.

## 4. Core domain model and data integrity

### 4.1 Global conventions

- Internal IDs are stable UUIDs; upstream keys are stored as `(provider, provider_id)` unique pairs; never equate a provider ID with an internal UUID.
- All stored datetimes are timezone-aware UTC. API timestamps are ISO-8601 UTC (`...Z`). Frontend chooses display timezone.
- Use `created_at`, `updated_at`; use soft deletion/visibility for community and shared AI data. See mandatory `prediction_revisions` and `prediction_requests` entities for edit auditability and persistent replay.
- Primary league is `competition.code = "PL"`; other codes need metadata rather than hardcoded frontend behavior.
- Match status canonical enum: `SCHEDULED`, `LIVE`, `HALFTIME`, `FINISHED`, `POSTPONED`, `CANCELLED`, `SUSPENDED`, `UNKNOWN`. Provider status mapping must be explicit and logged.
- `data_source`: `DEMO_SYNTHETIC` or `LIVE_PROVIDER`; `last_synced_at`, `data_version` and `is_stale` indicate provenance.
- Distinguish `SCHEDULED` (a planned match), `LIVE` (actual provider-reported play), and venue illumination (selected-round presentation). Never infer live from scheduled kickoff alone.

### 4.3 Match evidence and venue provenance

Store match facts with a stable per-record source reference: e.g. `MATCH:abc123`, `EVENT:evt_01`, `STANDINGS:snapshot_42`. For AI analysis, construct a snapshot including facts, source refs, observed times, and whether fields are provider verified. The idempotent What-if request records its immutable request hash, lease ownership/expiry, retry count, serialized final success response and quota-charged timestamp; an indexed restart recovery scan reclaims expired leases. Do not fabricate a source ref for user assertions. Coordinates must be verified against source or curated venue data before exposed by `/map`; absent coordinates → `StadiumMapResponse.unmapped_matches` with an explicit `reason` and list-only fallback; `map_visible` is not a contract field.

## 5. External data and synchronization

Implement a `SportsDataProvider` protocol with `list_teams`, `list_matches`, `get_match`, `get_standings`, `get_match_events`, `get_venue`, and capability flags (`has_lineups`, `has_events`, `has_player_stats`). Each call returns normalized objects or `DataUnavailable` with reason.

**Default provider `demo`:** deterministic **fictional results and events** and plausible fixture assignments with an explicit `DEMO_SYNTHETIC` source label. For the England map, use real stadium/venue locations **only from a verified and attribution-safe curated venue file**, and set `coord_verified=true` only for those records. Otherwise set null coordinates and put matches in `unmapped_matches`; NEVER invent coordinates or an undocumented `map_visible` DTO field. Match simulations at real stadiums must remain prominently synthetic. `DEMO_CLOCK_ISO` (Appendix A1/A4) is read **only on first database seeding**; every subsequent demo-time decision and `/meta.server_now_utc` uses the persisted locked `app_runtime_state.demo_clock_utc`. Match-status and score changes happen **only** through explicit manifest-backed `demo_transition` scenario commands; manually advancing/injecting clock affects cutoffs but NEVER changes status/score/standings or settles predictions. There is no public mutation endpoint.

**Conditional P1 provider `football_data` (NOT a Phase 1 P0 gate requirement):** only when terms/licensing and credentials are available, integrate football-data.org v4 EPL (`PL`) competitions/teams/matches/standings endpoints. This source can support fixtures/scores/tables; **do not assume** it provides player-level substitutions or full live event timelines under the selected plan. If detailed events are missing, the What-if service explicitly returns limited-evidence analysis, never makes up substitutions. Document alternative enhanced provider as Phase 2 integration. Do not expose provider tokens to client.

Sync logic: upsert by `(provider,provider_id)`; transactionally map foreign keys; cache upstream results; respect 429 `Retry-After` and configurable request quota; exponential backoff with jitter on transient 5xx; keep last-known-good data marked stale on provider outage. Run sync manually or via single designated worker; do not schedule per API process. Sync matches & standings at modest configurable intervals (e.g. every 15 min normal, 2 min live **only when quota permits**). Transition to FINISHED only upon authoritative source status. On completion run settlement idempotently. All provider ingestion must preserve historic source/version lineage required by What-if evidence and impact.

Before production feed activation, confirm the chosen provider's license permits display, caching, derived analysis, and any future redistribution. Protect stadium imagery, club crests, and tournament trademarks separately.

## 6. API conventions and canonical DTOs

Base prefix `/api/v1`. Public GETs may be accessed anonymously; mutations require an authenticated session. All responses JSON except OpenAPI. Query bounds and pagination mandatory for lists (default `limit=20`, max `limit=100`, `cursor` where needed). Standard success uses returned object directly (no arbitrary double envelope). Standard error:

```json
{"error":{"code":"MATCH_NOT_FINISHED","message":"What-if analysis is available after full time.","details":{},"request_id":"req_a1"}}
```

Error mapping uses the exact status and code catalog in Appendix A1: notably invalid input is 422, authentication is 401, permission/Origin is 403, match-state conflicts are 409, provider errors 502 and AI errors 503. Use required UUID `Idempotency-Key` on prediction mutations and What-if messages; implement replay and key/body conflict rules from Appendix A3.

All DTO fields, nullable behavior, response envelopes, list ordering, complete stadium fixtures, Impact-with-embedded-match, profile and room-detail shapes, authentication responses, and AI retry semantics are frozen in **Appendix A3**. Do not maintain conflicting parallel DTO examples in this section. Read the canonical types there before implementing any route.

### 6.3 AI message contract — most important endpoint

**Request:** `POST /api/v1/whatif/threads/{thread_id}/messages`, mandatory UUID `Idempotency-Key`, body `{message:string,client_message_id:UUID}` (10–2,000 chars). The authoritative 200/202/503 response shapes are `WhatifTurnResponse`, `WhatifPendingResponse`, and the error envelope in Appendix A.

**Verdict enum:** `PLAUSIBLY_BETTER`, `PLAUSIBLY_WORSE`, `NO_CLEAR_DIFFERENCE`, `UNCERTAIN`, `INSUFFICIENT_DATA`, `INVALID_PREMISE`. Confidence is qualitative LOW/MEDIUM. No numeric counterfactual outcome probability.

**Service workflow (execute in this order):**

**Thread concurrency invariant:** After auth + ownership and SAME-KEY idempotency lookup, serialize NEW/different-key What-if messages per thread under a thread-row lock. At most one PENDING turn may exist per thread; a different key arriving while PENDING returns 409 `WHATIF_THREAD_BUSY` with `details.active_client_message_id` and `details.retry_after_seconds`, BEFORE quota reservation or a new USER row. Same-key retries still return 200/202 and never produce 409 BUSY. Release thread on COMPLETE/terminal FAILED and ensure the next accepted turn uses the completed preceding AI answer. Worker compares lease + demo_epoch before commit; stale epoch results are discarded.

**Retry invariant:** Authentication and resource ownership precede **persistent idempotency lookup**, which precedes daily quota, match state and new admission checks. Existing completed keys replay durable 200 snapshots irrespective of time/quota; pending keys yield 202, expired PENDING keys resume the reserved request after lease reclamation; an older FAILED request superseded by a newer USER turn yields 409 `WHATIF_TURN_SUPERSEDED` **before** quota checks; an eligible latest-turn FAILED key first atomically reacquires a quota slot for the authoritative **retry** UTC day, or return 429 without new USER/model/charge. Request hash/client-key mismatches yield 409. New admissions acquire atomic provisional quota slot; charge exactly once upon verified COMPLETE, and persist the AI turn + snapshot in the same transaction. See Appendix A3 for the full lease/recovery protocol.

1. Authenticate session and owner; resolve persisted `Idempotency-Key` + `client_message_id` (same content returns cached/202 or resumes). For *new* submissions only, check FINISHED match, daily admission/reservations, safety and 10–2,000 characters.
2. In one transaction store the immutable request hash, current reservation/charge day, one USER turn, recovery lease and pending request; load conversation's last 10 turns and immutable match evidence snapshot (score, events, lineups when truly available, standings if relevant).
3. Parse referenced people/events against verified match roster/events. If contradiction is demonstrable, return `INVALID_PREMISE` and point to the relevant facts. If necessary facts unavailable, return `INSUFFICIENT_DATA` (model may still discuss *general* conditional reasoning if clearly labeled).
4. Prepare AI instructions: *user's idea is a hypothesis, not evidence*; compare arguments for and against; cite only provided source IDs; separate observed vs speculative; suggest a thoughtful next question; never invent match events/stats or exact alternative result; keep response concise and respectful.
5. Call configured LLM adapter using strict JSON schema and a hard timeout. Both the offline scripted adapter and the **functional remotely configured model adapter** must implement the same interface; model output is untrusted and subject to the same evidence validation. G4 requires an optional-network, credentials-gated **real** unscripted novel-hypothesis + context-aware follow-up acceptance run; record unavailable credentials as BLOCKED, not a passing test. Messages, provider data and public chat are treated as **untrusted content**, not instructions to execute.
6. Validate parsed JSON (Pydantic), all `evidence_refs` against supplied evidence set, numbers/names/event minutes against normalized records, and absence of prohibited deterministic outcome claims. If invalid, optionally retry once with feedback; otherwise return safe fallback `INSUFFICIENT_DATA` / service error.
7. Only the current lease owner transactionally stores the validated AI turn, source references, model ID, response snapshot, and one quota charge; later-turn context excludes failed/unanswered earlier USER messages. ## 7. Deterministic scoring, rankings, badges

### 7.1 Prediction lifecycle

- A user can create/update **one** pre-match prediction per match using a UUID `Idempotency-Key` while `status=SCHEDULED` and server UTC `now < kickoff_at` (transaction-level check). Server rejects after cutoff, even if frontend timer is wrong.
- `outcome` required. Optional exact score must be nonnegative integers and internally consistent with outcome. Upstream later schedule changes cannot silently re-open locked predictions; editor-controlled policy needed if a fixture is postponed.
- On authoritative `FINISHED`, one idempotent settlement job assigns **3 points for correct outcome + 2 extra for exact score**; incorrect predictions yield 0 unless score-specific bonus eligibility is satisfied (never award exact-score bonus if outcome wrong). Mark `SCORED`. Cancelled/postponed matches `VOID`; suspended unknown remains `PENDING` until official resolution.
- Leaderboard sorts by points descending, then earlier confirmed `submitted_at`, then stable UUID; show equal point totals as equal rank in UI even when stable submitted-at ordering differs. The deterministic rule is documented and user-visible.
- Basic badge `PREDICTOR_BRONZE`: minimum **5 SCORED predictions**, outcome accuracy **≥60%**, calculated over up to **20 most recently SCORED predictions ordered by `scored_at DESC, prediction.id DESC`** (not submission time); VOID/PENDING excluded. Badge disappears from active display if moving-window conditions fail; keep badge history. Seed demo profiles with multiple synthetic historic predictions if showing badge in demo.
- Objective prediction badges ≠ analytical AI feedback badges. An AI-reasoning badge requires a separate policy and review in Phase 2.

### 7.2 Community ranking and visibility

For Phase 1 expose `public_badges` in `AuthorPublic` and `prediction_summary` in `UserProfile` exactly as Appendix A3. Do not permanently hide newcomer contributions. Default room sort chronological with optional `most_relevant` setting reserved for Phase 2; do not fake a quality rank from payment tier or message count.

## 8. Standings and personalized impact engine

**Do not ask an LLM to calculate league points or positions.** EPL current default rule set: win = 3 pts, draw = 1, loss = 0. Build this as a versioned competition rule module, with configurable tiebreak details; do not assert a definitive table position when teams remain tied and the full official tie-break cannot be resolved.

Inputs: official or replay-constructed **pre-match** standings snapshot (or for FINISHED, last snapshot before match/round + verified post-result snapshot), favorite team, target match, remaining fixture statuses, applicable rules version. The fixture own-team case is handled explicitly as described in Appendix A3b. Output: `HIGH|MEDIUM|LOW|NONE|UNKNOWN` relevance (HIGH 0–3, MEDIUM 4–6, LOW 7–9, NONE 10+ points away in other-team match), affected opponent(s), calculated points-gap deltas for home/draw/away results, and a clear `is_hypothetical` flag. A FINISHED match returns its one confirmed observed scenario plus two expressly hypothetical alternatives; all use historical pre-match evidence. `NONE` means **below the configured points-gap recommendation threshold** (minimum distance >=10), NOT zero calculable standings effects; its valid scenarios may still change gap values. It is excluded from the personalized relevance feed but remains accessible from match discovery and direct Impact.

**Important:** A points-only win/draw/loss selector can prove points-gap effects; exact ranking may need hypothetical scores because goal difference and goals scored can decide ties. For a scenario where tie-breakers are undetermined, set `position_change=null`, provide `position_note`, and never fill it with a guess. `position_change` consistently refers to the **favorite team’s** movement, not the named affected rival. Where verified completed-result snapshots exist, return the confirmed actual case and separately labelled hypothetical standings alternatives from the same historical baseline. The generic `/standings` endpoint supplies the **latest table**, not the historical pre/post snapshots; UI labels them separately.

AI only paraphrases a machine-produced `ImpactInsight`; robust template wording is the required fallback. Validate any AI text's numbers/team names and status against the calculated input. If standings data is absent, return `UNKNOWN`, not a plausible-sounding invention.

Unit tests: non-relevant opponent, nearest competitor, exact draw, tie requiring goal difference, invalid favorite ID, stale standings, completed snapshot vs projected round, relegation-zone scenarios only when metadata supports it.

### A1. Transport, authentication, time, errors, and scope

- **Base path:** Every path in A2 is relative to browser-facing `/api/v1`. Next.js rewrites `/api/v1/:path*` to `http://localhost:8000/api/v1/:path*` in local development; browser requests stay same-origin (`http://localhost:3000`). Do not use a cross-origin direct-browser API URL in Phase 1. Backend OpenAPI at `/openapi.json`; health at `/api/v1/health`.
- **Cookies and CSRF:** Browser session is an opaque HttpOnly cookie named `matchline_session`, `Path=/api/v1`, `SameSite=Lax`, `Secure` in HTTPS; no bearer tokens in browser JS. Register/login/logout **and all authenticated mutations** require a valid exact-match `Origin: http://localhost:3000` in development (production uses configured exact frontend origin). Browser POST/PUT/DELETE use `credentials: 'include'`, JSON body, and ordinary browser Origin, with no custom CSRF token/header. Requests lacking a valid Origin are rejected 403 `CSRF_ORIGIN_INVALID`; test clients must supply Origin; trusted CLI integration runs inside app/DB rather than bypassing browser security. `GET` requires no Origin. Never rely on CORS alone.
- **IDs / clocks:** All resource identifiers ending `id`/`_id` (including `client_message_id`) and `Idempotency-Key` use canonical UUID strings. **Exception:** transport/log correlation `error.request_id` is a non-resource opaque string such as `req_01AB`; `source_ref`, `data_version`, cursors, and provider identifiers are also not constrained to UUID. All API timestamps use UTC RFC3339 `YYYY-MM-DDTHH:mm:ssZ`. `season=2026` means 2026–27 season **start year**. Calendar `date=YYYY-MM-DD` is Europe/London civil date; backend applies DST-correct IANA conversion and filters UTC kickoff instants within that local day. Frontend formats match time in Europe/London (with timezone label). Numeric scores/position/coords are genuinely nullable; never invent missing data.
- **Demo clock:** `GET /meta` includes `server_now_utc`, `demo_clock_frozen:boolean`, `mode: 'DEMO'|'LIVE'`, `default_competition:'PL'`, `default_season_start_year:2026`, `demo_epoch:number|null`, `scenario_revision:number|null`, `capabilities:{whatif_sharing:false,events:boolean,live_updates:boolean}`. In DEMO the backend reads a **single injected/fixed clock** (`DEMO_CLOCK_ISO=2026-10-24T12:00:00Z` is used ONLY during first seeding; persisted singleton `app_runtime_state.demo_clock_utc` is authoritative thereafter, re-read on every API request); all prediction cutoffs, room locks, quotas and source-as-of calculations use it. Frontend derives the visible `Demo as of <formatted /meta.server_now_utc>` label **dynamically on every `/meta` refresh** (for example, first baseline `Demo as of 24 Oct 2026, 12:00 UTC`); later scenario transitions must update this display. It **must not** show a real-time ticking countdown against a frozen clock. The management command `python -m app.jobs.demo_transition --scenario baseline|upcoming_live|upcoming_finished` atomically applies scenario-specific **explicit match status + verified synthetic scores/events + standings snapshots + clock** from the seeded manifest. Merely advancing/injecting the clock NEVER promotes SCHEDULED to LIVE or FINISHED, populates scores, or runs settlement. Only the `upcoming_finished` transition runs deterministic prediction settlement for that match. Do not expose any public demo mutation route. In LIVE mode `server_now_utc` is request time; client countdown is informational only; server remains authoritative.
- **Enums:** `MatchStatus=SCHEDULED|LIVE|HALFTIME|FINISHED|POSTPONED|CANCELLED|SUSPENDED|UNKNOWN`; `Illumination=UPCOMING_ROUND|LIVE|COMPLETED|INACTIVE|POSTPONED_OR_CANCELLED|UNKNOWN`; `Plan=FREE|PREMIUM`; `Role=USER|EDITOR`; `RoomKind=PRE_MATCH|POST_MATCH`; `RoomStatus=OPEN|READ_ONLY|HIDDEN`; `Relevance=HIGH|MEDIUM|LOW|NONE|UNKNOWN`; `SourceKind=DEMO_SYNTHETIC|LIVE_PROVIDER`; `PredictionStatus=PENDING|SCORED|VOID`; `Outcome=HOME|DRAW|AWAY`.
- **Errors (all non-2xx JSON responses):** `{ "error": { "code": "STRING_ENUM", "message": "Readable message", "details": {}, "request_id": "req_..." } }`. Codes/status: `UNAUTHENTICATED` 401; `FORBIDDEN`, `PREMIUM_REQUIRED`, `CSRF_ORIGIN_INVALID` 403; `NOT_FOUND` 404 (includes threads owned by another user and any room that is hidden/not yet discoverable, including its messages, changes, and posting paths; no room-existence leak); `PREDICTION_CLOSED`, `ROOM_CLOSED` (includes room creation after PRE_MATCH cutoff or before verified POST_MATCH finish), `MATCH_NOT_FINISHED`, `IDEMPOTENCY_CONFLICT`, `WHATIF_THREAD_BUSY`, `WHATIF_TURN_SUPERSEDED`, `WHATIF_THREAD_LIMIT` 409; `INVALID_INPUT` 422; `RATE_LIMITED` 429 with `details.reset_at` in UTC; `PROVIDER_UNAVAILABLE` 502; `AI_UNAVAILABLE` 503 with `details.client_message_id` and `details.request_state`. `WHATIF_THREAD_LIMIT` is returned only for a **new distinct** user turn beyond the 40-turn thread cap; the error uses the standard envelope with `details.limit=40` and `details.admitted_turns=40`, persists no new turn, and consumes no daily quota. Exact-key replay/retry of an already admitted turn retains its original documented behavior, even if the thread is at the cap. Insufficient evidence or invalid hypothesis in a *successfully processed What-if* is HTTP 200 with a verdict, **not** an HTTP error. Invalid credentials return 401 `UNAUTHENTICATED`. Nullables are explicit, not silently omitted.
- **List envelopes:** Ordinary paginated list is `{items:[...],next_cursor:string|null}` (default limit 20, maximum 100); the room-message list is explicitly `RoomMessagesPage` with additional `sync_after_seq`, and the room change feed is `RoomChangePage` with its own sequence cursor. `GET /teams`, `/competitions`, `/competitions/{code}/matchdays`, `/users/me/badges` and `/matches/{id}/leaderboard` return `{items:[...]}` without cursor. Other lists are newest-first unless otherwise specified; Journey is chronological ascending, standings are position ascending. **Room-message pagination has two explicitly different modes:**
  - **Initial and older-history mode:** `GET /rooms/{id}/messages?limit=N` returns the **latest N public-visible** messages, displayed ascending by `(created_at,id)` within the page. `next_cursor` is an opaque, room-bound **backward** cursor for strictly older messages: `GET ...?cursor=<next_cursor>`. Older pages are also ascending and are prepended; `next_cursor=null` means history exhausted.
  - **Forward catch-up mode:** `GET /rooms/{id}/messages?after_id=<last_seen_message_UUID>&limit=N` returns the **earliest N currently public-visible messages strictly after the referenced stored message's `(created_at,id)`**, ascending. `after_id` may refer to a message since hidden by a moderator; the server resolves its stored sort key but never returns its hidden contents. In this mode `next_cursor` is **always null** (the older-history cursor is not repurposed). The client advances `after_id` to the last ID received and requests again until a page has fewer than `limit` entries (an exactly-full page requires another fetch). A room-mismatched/unknown `after_id` is 422 `INVALID_INPUT`. `cursor` and `after_id` cannot be used together (422). For a busy room, cap pages per UI polling cycle but continue catch-up from the last processed ID next cycle; do not skip IDs. Timestamp ties are broken by UUID, never offsets. After demo-epoch reset/relogin, clear old anchors and fetch the initial window again. A first-load page may be empty; no forward anchor exists until a message is observed.
  - **Public moderation semantics:** only `VISIBLE` and `FLAGGED` rows are returned; a `FLAGGED` report is not automatic hiding. `HIDDEN` rows are excluded entirely from public message responses (**no placeholders or empty-body leaked metadata**) and from `RoomSummary.message_count`. Public `RoomMessage.moderation_state` is therefore only `VISIBLE|FLAGGED`; editors can audit hidden rows through private backend tooling outside these public DTOs. Use the room `/changes` feed to evict a hidden message from **all cached pages**, including loaded older history; never reveal the removed text or author data in placeholder messages. On reload, fetch an initial atomic room snapshot and resume from its returned sequence watermark. Rate-limited polling must retain its forward anchor and reconnect on the next cycle.
  - All reads are deterministic keyset queries; use the same visibility filter for older/forward/initial windows, ensure no overlaps, de-duplicate UUIDs, and render the combined visible timeline in `(created_at,id)` order. Never rely on refetching only the latest page to discover all intervening messages.
  - **Authoritative empty-room and moderation-safe sync (v2.4):** `GET /rooms/{id}/messages` returns `RoomMessagesPage` (the existing page fields **plus `sync_after_seq:number`**). On **initial** fetch the server reads the visible latest window and the per-room committed high-water event sequence in one consistent database snapshot; a returned empty `items=[]` still has a usable sequence. The client retains this initial watermark and uses `GET /rooms/{id}/changes?after_seq=<sequence>&limit=N` for incremental updates, including after an empty initial page; an `after_id` anchor is **not** required. Older-history `cursor`/`after_id` remain supported, but the v2.4 UI uses the change feed as its authoritative live sync and cache-removal mechanism. `RoomChangePage` returns earliest events strictly after `after_seq`, sequence-ascending, with `next_after_seq` equal to the last processed event sequence (or the supplied sequence if none) and `has_more`; the client must continue until `has_more=false`, even across polling cycles. Event seq is room-scoped, monotonically increasing and allocated transactionally on message insert, moderation FLAGGED update, and HIDDEN removal. `UPSERT` contains the **current** public-visible `RoomMessage`, whereas `REMOVE` contains only message UUID and event seq (never content or author metadata); querying an historical `UPSERT` after its message becomes HIDDEN must yield a content-free `REMOVE`, not the formerly visible text. On receipt of `REMOVE`, evict that ID from **all cached history pages**, including far-back pages; on `UPSERT`, insert/update by ID in chronological order. No event-body snapshots from formerly visible but now HIDDEN posts may be exposed. Subsequent paginated older reads must also filter hidden rows. The backend ensures a snapshot/query-bound sequence watermark and does not skip an event if new writes arrive during catch-up; event pages are fetched from the committed per-room sequence while clients continue from the returned `next_after_seq` only, not a wall-clock timestamp. `after_seq` must be an integer >=0 and <= current room sequence; invalid values -> 422. This endpoint complements older-page cursors; it does **not** expose private moderation notes. After demo reset, re-authentication and demo epoch revision, discard room caches and sequence watermarks. Test: empty initial window → 45+ additions at limit=20 → all appear exactly once; hide an old cached message → REMOVE evicts it regardless of loaded page depth; request feed starting at 0 after moderation never leaks old body, retains original event sequence numbers, and paginates across redacted UPSERTs without gaps or altered page-size limits.
