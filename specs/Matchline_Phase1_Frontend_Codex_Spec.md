# MATCHLINE — Phase 1 Frontend Implementation Specification

**Document ID:** ML-FE-P1  
**Version:** 2.4 (end-to-end workflow and contract reconciliation) · 24 October 2026  
**Audience:** Frontend engineer / OpenAI Codex agent  
**Product:** Matchline (working name)  
**Canonical API:** Both specifications carry the identical frozen contract in Appendix A. Backend `/openapi.json` must conform to that contract; frontend generates types only from conforming OpenAPI. Neither agent may change the contract unilaterally.  
**Status:** Reviewed and harmonized against backend v2.4; implement matching frozen contract and explicit mock fixtures. BE-00/FE-00 bootstrap precedes G0.

> **Most important UX rule:** The post-match **What-if experience is a conversation between the user and AI**. The user types an alternative football scenario or disagrees with AI; AI critically analyses that idea using **verified match evidence**, says what supports/challenges it, communicates uncertainty, and invites follow-ups. This is not just a forum, not merely a one-shot question form, and not a model pretending to know the result of an unplayed scenario. Community rooms are separate; excerpt sharing is deferred to Phase 2 with explicit consent and review.

## 1. Product identity and phased implementation

**Product promise:** "Follow your team as a journey; discover why every match matters; challenge football decisions with fans and AI."

The user's first reason to enter is the **Candy Crush-inspired Match Journey**. Match personalization supplies relevance; pre/post-match participation sustains engagement; AI provides grounded feedback; reputation grows with objectively scored predictions. A second geographic map provides stadium discovery and favorite-team impact.

### 1.1 Two implementation phases

| Experience | Phase 1 (deliver working MVP) | Phase 2 (expand) |
|---|---|---|
| Home Journey | Accessible responsive vertical/winding match path, competition-themed nodes, status, match details | Rich transitions, multiple competitions and followed teams, deeper progression/gamification |
| Map | England venue map, date **or** matchday selection (mutually exclusive), dim/live/result states, favorite/impact highlights, accessible list fallback | Live push, more leagues/countries, map/table overlays, personalized map modes |
| Personalization | Team onboarding, guest local preference + authenticated saved preference, **basic deterministic favorite-fixture + Impact recommendations** (no extra API), all matches still accessible | Multi-team favorites, **learned/behavioral recommendations**, alerts, notification center |
| Community | Browse/read rooms, FREE can post, PREMIUM can create, post-match rooms, badges beside authors | Reactions, threaded replies, advanced moderation, sorting and creator tools |
| Prediction | Simple structured outcome/score widget, lock at kickoff, result and basic leaderboard/badge | AI extracts user claims from text, explainability, leaderboards, appeals and seasonal rankings |
| What-if | **Private multi-turn user ↔ AI conversation**, evidence cards, supports/challenges, uncertainty, chat history; no sharing in Phase 1 | Shared group analysis, compare branches, streaming AI, sources/media, collaboration and export |
| Impact | Personalized match relevance, exact points-gap scenarios, no unsupported exact positions | Multi-round simulator, goals/tiebreaker scenarios, longer-term significance |
| Access | Login/register and local demo premium features, accessible paywall info | Production subscriptions and paid account management |
| Ecosystem | Only internal source/consent-compatible UI | Developer portal, integration marketplace, API-based content embeds |

**Phase 1 release demo path:** select Arsenal → see team Journey → click an upcoming match → check match preview and pre-game room → post an opinion and submit a structured prediction → see personalized impact of another game → explore live/finished stadium states → open a completed match → debate substitution with AI over 2+ turns → view evidence/uncertainty → see profile prediction history and badge. AI sharing is disabled throughout Phase 1; it will be designed with consent and moderation in Phase 2.

**Source note:** Match results shown in local fixture mode are **DEMO / SYNTHETIC** and must have a visible label. Real data mode depends on upstream rights and credentials; missing provider details must appear as unavailable, not invented.

## 2. Recommended frontend stack

- **Next.js App Router**, TypeScript strict, React and Tailwind CSS; maintain component accessibility and simple semantics. Use currently supported stable releases locked by `pnpm-lock.yaml` or npm equivalent; no canary packages.
- Reusable accessible UI primitives (`shadcn/ui` / Radix where convenient) for dialogs, cards, tabs, select, toast, tooltip, disclosure and form.
- **TanStack Query** for server state, caching, loading/error/refetch; `React Hook Form` + `Zod` for mutation forms; lightweight React Context for active team and auth state (avoid duplicating remote data).
- **React Leaflet / Leaflet** for England geographical map. Render map in **client-only dynamic component** (no SSR) and import Leaflet styles; supply a keyboard-accessible linked list view for map markers. Use a configurable tile provider, clear attribution and obey tile usage policy; map works with mock marker data while external tiles unavailable.
- **SVG / CSS for Journey** (no canvas required). Each node is an actual keyboard-focusable `<button>`/`<a>` with `aria-label`, not an invisible clickable SVG-only hotspot. `prefers-reduced-motion` disables pulse/wiggles.
- Next.js frontend **always** calls same-origin `/api/v1/*` in Phase 1. Configure a server-side rewrite/proxy (local development example: `/api/v1/:path*` → `http://localhost:8000/api/v1/:path*`) using **server-only** settings; never expose or use `NEXT_PUBLIC_API_BASE_URL`, direct cross-origin browser API calls, or browser-supplied AI/sports API secrets. Browser credentials are sent to its own origin and backend validates the configured exact `Origin` on mutations.
- Vitest + React Testing Library + MSW for component/unit/API mocks; **Playwright** for end-to-end user flows. ESLint + TypeScript typecheck.

## 3. Navigation, routing and information architecture

**Primary navigation, in this order:** `Journey` (homepage) → `Map` → `My Team Impact` → `Community` → `Profile`. The external developer experience is NOT a fan-facing Phase 1 tab.

| Route | Main content | Auth / behavior |
|---|---|---|
| `/` or `/journey` | Personalized winding season match path; focused on next match | Public; if guest favorite absent, show team-picker first, still allow browsing |
| `/matches/[id]` | Match summary, events, pre-/post-match actions, What-if chat | Public for details; posting/AI requires login |
| `/map` | England map with verified active/inactive stadiums, matchday selector and list fallback | Public; favorite highlighting when configured |
| `/impact` | Favorite-team relevance feed + standings and caveats | Public with team-picker; user team from profile or guest setting |
| `/community` | Match-room discovery and access | Public read; login required to contribute |
| `/community/rooms/[id]` | Single room detail and messages; refresh-safe and shareable deep link | Public read via `GET /rooms/{id}`; logged-in FREE/PREMIUM can contribute if OPEN |
| `/profile` | G3: favorite team, plan, prediction history and badges; G4: private What-if thread list | Auth required; friendly sign-in CTA for guest; G3 does not require BE-08 |
| `/login`, `/register` | Account entry; preserve return-to destination | Public |
| `/premium` | Explains creator-only premium access; **mocked payment** | Public informational; do not claim payment made |

Routes must be direct-linkable and refresh-safe. Opening `/matches/[id]?tab=whatif` should reach What-if panel even without visiting Journey. Opening `/community/rooms/[id]` must fetch the room directly from `GET /rooms/{id}` rather than relying on a previously loaded room list; test reload, invalid ID, and permission-denied posting. Treat AI history as private: guard UI and rely on backend owner authorization.

### 4.1 Competition vs status must never conflict

**Competition identity:** primary node fill/stroke + generic motif and small label. Examples:

- Premier League: blue + minimalist crown/football motif (create original artwork, do not copy league logo).
- Champions League: purple + original stars/radial pattern motif, distinct from official trademarked starball.
- FA Cup: orange + generic cup silhouette.
- EFL Cup: cyan + generic trophy silhouette.
- Europa League: green + angular shape motif.
- Unknown: gray + neutral ball motif.

**Status identity:** independently rendered ring/icon and text:

- UPCOMING/SCHEDULED: calendar or clock icon, no animation.
- LIVE / HALFTIME: status label and animated outer ring (respect reduced motion); for HALFTIME show explicit `HT`.
- FINISHED: final score/check icon; node remains competition-colored.
- POSTPONED/CANCELLED/SUSPENDED: warning/paused badge, disable prediction submission, explain state.
- UNKNOWN/stale: question/data warning; never invent status.

No visual signal can rely on color alone. Each node's accessible name includes both competition and status. Provide a legend always accessible via screen reader and visual button.

## 5. Page specifications and interaction behavior

### 5.1 Onboarding and favorite team

**Initial state:** when no `favorite_team_id`, show welcome panel with searchable/selectable EPL team cards (name and crest when licensed, text fallback). Selection immediately shows a temporary personalized preview. For signed-in user call `PUT /users/me/favorite-team`; for guest persist team ID in localStorage `matchline:favorite_team_id:v1`. On login/register, fetch authenticated `/auth/me` and use only its server `favorite_team_id` (including null) for all signed-in personalization. If an older guest-local favorite differs, show an explicit import decision; do not apply or sync it until the user affirmatively opts in and a `PUT /users/me/favorite-team` succeeds. Decline leaves the server value unchanged. On logout, clear session-specific room/Impact caches and return to guest browsing; never render a previous account's favorites/permissions. Show a small toast on successful change; update all dependent query keys.

**Requirements:** one favorite at a time; change through Profile/team menu; preserve historical badges and predictions; no favorite = browse the public all-matches discovery returned by `GET /matches?competition=PL` (Journey requires `team_id`) and make the favorite-team choice visible. Team ID must come from API, not hardcoded names.

**Acceptance:** team selection survives reload; logged-in user survives new browser session via server; changing team updates Journey, Map, Impact; all-matches list remains reachable; absent team list yields retry and informative empty state.

### 5.2 Journey — central feature

Layout: centered, responsive winding path of cards/nodes; default focus is the nearest upcoming fixture. Desktop nodes follow slightly offset alternating sides; mobile uses vertical path. Do not clone Candy Crush branded illustrations; borrow only the *progression pattern*. SVG curved connectors behind accessible HTML node buttons (decorative SVG aria-hidden). At 20+ fixtures, use incremental rendering or pagination to avoid long initial layout.

Node must display competition motif, opponent short label, home/away, day/time or full-time score, match status, and optional favorite-related highlight. Each click opens `/matches/[id]`. Small adjacent affordances show pre-match room/prediction if scheduled; live information if playing; post-match room/What-if if completed; each state is based on the API `features` object rather than browser guesses.

Example conceptual arrangement:

```text
                 MATCHLINE / ARSENAL                    [Change team]
             Season 2026/27    [All] [League] [Cups]

                       (PL / blue)  ✓  2–0
                      Arsenal — Opponent A
                              ╲
                         (UCL / purple + stars)  ○
                           Opponent B — Arsenal
                              ╱
                [NEXT] (PL / blue + clock)  ○  Sat 17:30
                         Arsenal — Opponent C
                         [Discuss] [Predict] [Impact]
                              ╲
                          (FA Cup / orange + cup)  ○
                               Future match
```

If Phase 1 provider only supplies Premier League, show only real PL fixtures; **do not manufacture Champions League matches**. Competition motifs are implemented in theme system and can be demonstrated with explicitly synthetic demo fixtures and feature toggles. Disabled competition filters must explain missing data rather than show empty artificial seasons.

**Acceptance:** keyboard navigation logical; nearest upcoming fixture centered or highlighted; status changes do not alter competition color; unknown competition uses neutral motif; direct links work; mobile has readable tap targets; missing crest/image doesn't break layout.

### 5.3 Match Details — pre/live/post state machine

Sticky header: Home/Away team, scores or kickoff, competition, matchday/round, stadium and source badge. Sections can be tabs: `Overview`, `Discuss`, `Predict` (before), `What-if` (after), `Impact`, `Events` if available. Keep one accessible match summary at top. Provide explicit labels:

- **Upcoming:** verified date/venue, standings context, `Join discussion`, `Submit prediction`, possible effect on favorite team, data capability messages when H2H/form unavailable.
- **Live:** current verified score/status and last sync time; pre-match predictions locked; do not open What-if before FINISHED; show live discussion placeholder unless implemented.
- **Finished:** final result, verified event timeline and stats when data exists, read-only pre-match discussion, post-match discussion, prediction outcome, **Talk to AI: What if?** entry point.
- **Postponed / cancelled:** no fake full-time display, no new prediction or what-if, clear reason/unknown text.

Never show a scorer, substitution minute, possession or player stat that backend did not provide. Use `Not available in current feed` instead.

### 5.4 What-if panel — **the core interactive AI feature**

**Entry point:** finished match page, prominent button `Debate this match with AI` / `What if...?`. Opens an embedded conversation panel or dedicated sheet with persistent thread list. User can start multiple threads for the same match, each with a title (derived from first user prompt or default; editable only if backend supports).

**Structure of panel:**

```text
┌────────────────────────────────────────────────────────────────┐
│ What if?  •  Arsenal 2–1 Opponent  •  FINISHED  [AI analysis]  │
│ Ask about a real moment, decision or alternative tactic.      │
│ [What if the striker stayed on?] [What if the red card ...?]    │
├────────────────────────────────────────────────────────────────┤
│ YOU  "If we had kept the striker on, we'd definitely score."  │
│                                                                │
│ AI  "The idea is plausible, but 'definitely' is too strong."  │
│ Verdict: UNCERTAIN       Confidence: LOW                      │
│ What supports it?   [Verified substitution at 70'  ↗]          │
│ What challenges it? [No alternative scoring event exists]     │
│ Assumptions: continued effectiveness, same tactical approach  │
│ We cannot know: what chances would have occurred               │
│ "Would you like to examine chance creation rather than goals?" │
│ [How was this made?] [Private thread]                           │
│                                                                │
│ YOU  "But the opponent's defense was tired by then."          │
│ AI  "That adds a tactical hypothesis; the data we have..."    │
├────────────────────────────────────────────────────────────────┤
│ [Type your idea or challenge the AI...]          [Send]        │
│ AI counterfactual analysis — not an observed fact.             │
└────────────────────────────────────────────────────────────────┘
```

This is a **back-and-forth AI discussion**, not a list of users' what-if comments. Render each AI turn in digestible blocks: `Verdict`, `Reasoning`, `Supports`, `Challenges`, `Assumptions`, `Unknowns`, `Sources`, `Suggested follow-up`. Present challenges constructively, not as an absolute dismissal. Even where model says PLAUSIBLY_BETTER, always show the uncertainty disclaimer.

**Turn handling and reload recovery:** user types up to 2,000 characters; enter sends (Shift+Enter newline), while sending disable duplicate clicks; optimistic USER bubble is permitted with sending state; call `POST /whatif/threads/{thread_id}/messages` with generated `Idempotency-Key` and `client_message_id`. On success reconcile saved USER/AI messages. On error keep the same idempotency key, client message ID and byte-identical text attached to the attempted turn, refetch history, and retry without duplicating the optimistic bubble. Persist this attempt identity **per account/thread/client ID in tab-scoped sessionStorage** until successful reconciliation; store no auth tokens and clear on success/logout/account switch. If the attempt was not yet persisted by server before reload, retain the exact original body in tab-scoped attempt record solely for replay; delete on resolution. On reload fetch `/auth/me` and owner-only thread history; reconcile `client_message_id` and exact USER content before retry. Without a valid attempt record show a safe unresumable state rather than silently minting a new idempotency key. A FAILED request released its slot: same-key retry may receive 429 if retry-day quota is exhausted; show reset time and retain the attempt rather than claiming the retry is quota-free. The server may have saved the USER turn before the model failed. Never append a fabricated AI response. No client-side LLM key. State lives on backend and private thread history loads from `/whatif/threads/{thread_id}`.

**Grounding and explainability:** evidence chips expand the validated, embedded `AIWhatifMessage.evidence:WhatifEvidenceItem[]` discriminated records; no `/sources` lookup or inferred evidence resolver is allowed. Show source label and actual typed details (verified event minute, final score, standings snapshot/as-of, metadata, or evidenced player-season stat). Never claim the score at a substitution minute from final-score data. If `INVALID_PREMISE`, show correction and an editable follow-up suggestion. If `INSUFFICIENT_DATA`, show clear limitation and invitation to refine hypothesis. If `AI_UNAVAILABLE` transport/service error, preserve draft and allow retry, no fake model text. Label model text `AI analysis`; verified scores/events `Data`; user's statements `Fan hypothesis`. Quotes from user's idea are not marked verified facts.

**What-if and scoring:** This view may provide **qualitative reasoning feedback**, not an objective correctness rank. Do NOT turn conjectural outcomes into factual percentages or award prediction accuracy points. Phase 1 has no What-if share UI or share mutation: `/meta.capabilities.whatif_sharing` is always false. AI conversations remain private. In Phase 2, excerpt sharing requires consent, review before publication and revocation.

**Conversation-cap explanation:** Show `X of 40 questions used` (calculated from distinct admitted USER messages, not successful AI replies). A failed admitted question still uses one of those 40 lifetime thread slots; an exact-key retry does not use another. Distinguish this explicitly from the daily quota, which charges completed AI replies; if the conversation reaches the cap, show the 409 `WHATIF_THREAD_LIMIT` message and a Create new thread action.

**Quota and access:** signed-in FREE users get 3 completed AI turns per UTC reservation day; PREMIUM get 30/day (server response is authoritative); FAILED same-key retry must reacquire a released capacity slot in the **current retry UTC day**, and may return 429 without creating another USER turn; COMPLETE replay does not charge again; unauthenticated users see what the feature does and sign-in CTA. Do not show premium as the only way to use AI; premium differs in creation permission and larger AI quota. Quota exhaustion displays reset explanation / informational premium upsell rather than vague errors.

**User acceptance:** completed match → type idea → get evidence-supported critique → send follow-up → contextual answer; after refresh the same thread continues; a different user cannot view thread; an invalid substitution does not cause hallucinated timeline; no share or public excerpt publication exists in Phase 1.

### 5.5 Community and subscriptions

**Rooms are user-to-user.** Two kinds: PRE_MATCH and POST_MATCH. System-seeded rooms guarantee that all users can contribute even if no premium fan has created a room. Listing displays title, creator badge, reply count, open/read-only state. Inside room display messages chronologically, timestamps, author badge and report menu. Authenticated FREE and PREMIUM can post to OPEN rooms, and both can read all public rooms. PREMIUM can create a room through a titled form with match/kind selection; a real G2 integration test uses BE-03 local-only FREE/PREMIUM demo credentials supplied out of band, stored only in gitignored Playwright-runner configuration/secret environment (never NEXT_PUBLIC, committed fixtures, frontend bundle, or logs); FREE sees `Create room — Premium` with a concise reason and informational `/premium` link, but composer stays enabled for existing rooms.

Lock PRE_MATCH at cutoff and preserve it as historical read-only; POST_MATCH only after verified finish. A PREMIUM/EDITOR may create PRE_MATCH only when the match is SCHEDULED and the authoritative server time is **strictly before kickoff**; at/after kickoff or on another status creation returns 409 `ROOM_CLOSED` even when the fixture still displays SCHEDULED. POST_MATCH creation is allowed only when verified FINISHED. Disable create controls using the backend same-kind `can_create` permission when a relevant RoomSummary exists; for rooms not yet present use match status/time for a visual hint only and always handle server 403/409 as authoritative. For a seeded/unactivated or otherwise hidden room UUID, the room detail, messages, changes and posting endpoints uniformly return 404 `NOT_FOUND`; do not retry hidden content endpoints, fetch changes, or infer existence from a 404. Hide or disable actions with reason. The client is never the final permission authority: handle 403/409 gracefully. Phase 1 room messages use an active-tab short polling interval (e.g. 10–20 seconds), and **must use `/rooms/{id}/changes?after_seq=N` and the initial `RoomMessagesPage.sync_after_seq` for authoritative incremental catch-up**, even if the initial room page is empty and >20 messages arrive between polls. Continue while `has_more=true` (possibly across cycles), apply ordered UPSERT/REMOVE by UUID, and preserve scroll. Redacted historical UPSERT events retain their original `seq` as public content-free REMOVE; advance `next_after_seq` even when every row in a page is redacted, and treat repeated REMOVE operations as idempotent. `next_cursor` stays reserved for older history; `after_id` is an optional legacy forward method, not the primary UI sync path. Never promise WebSockets that aren't implemented.

**Moderation:** report action available to authenticated users; FLAGGED messages remain readable with a subtle report-state indicator until a moderator explicitly hides them. HIDDEN messages are **absent** from public API responses and MUST NOT display content, server-provided metadata or redacted placeholders. Apply content-free REMOVE events to evict newly hidden messages from **all** cached older/history pages, not only the visible window; optional local-only non-content scroll anchor is permitted. Never dangerously render arbitrary HTML; URLs only use safe protocols. Phase 1 has no editorial moderation dashboard or hide-message HTTP route; privileged backend staff use only the guarded local moderation CLI described in the backend specification, while the frontend consumes content-safe REMOVE updates.

### 5.6 Predictions, ranking and badges

Before kickoff render a clear prediction panel: three outcome choices `Home win`, `Draw`, `Away win`; optional two score inputs, with client-side both-or-neither score validation, nonnegative integer scores and selected-outcome consistency; deadline shown in user's local timezone. Client blocks the UI after API cutoff but **server** decides eligibility. When prediction is submitted, display `Pending · Locks at kickoff` and allow edits only before cutoff.

After FINISHED render an objective breakdown (`Correct outcome: +3`; `Exact score: +2` if matched; otherwise `0`), match leaderboard and badge conditions. For user profile show last settled predictions and `PREDICTOR_BRONZE` if minimum 5 settled with 60% correct, over the latest 20 settled predictions (or all available if fewer). No badges for unsupported speculative What-if "accuracy". Display author badge near community messages but do not bury all newcomer posts.

### 5.7 Geographical map

**Scope:** Map of England (not Finland), verified stadiums for season participants **and all verified venues hosting the selected fixtures, including neutral grounds with no home-club association**. Default filter is **date** equal to the Europe/London civil date of `/meta.server_now_utc` (DST-correct conversion); the user may deliberately switch to matchday. Never silently switch filters when the selected date has no fixtures: show the empty-day message and an explicit “View next available matchday” action. At top filter selected EPL matchday **or** date (mutually exclusive API filters). Place venue marker at coordinates only if `coord_verified=true`. If several matches use one venue in selected view, popup lists each complete `StadiumFixture.match` separately, without an N+1 fixture-detail waterfall.

`illumination_state` visual semantics:

| State | Visual behavior | Click rule |
|---|---|---|
| `UPCOMING_ROUND` | Soft warm light or subtle glow | Clickable match preview; label "scheduled" not "live" |
| `LIVE` | Bright green pulsing halo + LIVE label | Clickable score/impact |
| `COMPLETED` | Light off or subtle result label | Every selected FINISHED fixture is clickable regardless of whether the selector is a calendar date, a completed round, or a mixed-status matchday |
| `INACTIVE` | Dark/dim stadium with no active fixture in chosen round | Venue button disabled / informative hover, not misleading active match |
| `POSTPONED_OR_CANCELLED` | Muted warning symbol | If available, opens explanation; never display live |
| `UNKNOWN` | Neutral question mark and source warning | Do not infer active or live |

Favorite-team **verified home stadium** gets a subtle secondary outline when `StadiumVenue.home_team_ids` includes the favorite team, even if it is INACTIVE (zero selected fixtures); home affiliation must never be inferred from only the current round's matches. **Independently**, every selected `StadiumFixture.match` where `home_team.id === favorite_team_id` OR `away_team.id === favorite_team_id` gets a favorite-fixture marker in the popup/list, even when it is an away game at another club's ground or a neutral venue; this is distinct from the home-stadium outline and from other-team Impact relevance. Shared stadium may have multiple home teams. If verified association is unavailable, no home-outline is guessed. When neither an authenticated favorite nor an explicit guest-local favorite is selected, **skip all personalized Impact requests and indicators** while retaining the complete public map and a choose-team CTA. Other-team fixtures with HIGH/MEDIUM/LOW get a small **impact indicator**, UNKNOWN gets a neutral `Unverified` marker (never a high-relevance glow), and NONE has no indicator; do not replace live/competition state. The Impact feed request must use the selected `date` **or** `matchday` (same Europe/London selection as Map), traverse ALL pages and match by UUID; until complete or if failed, state `Impact loading/unavailable`, not `no impact`. Include legend and **accessible list of fixtures** directly beneath or beside map; matches with missing verified coordinates appear there labeled `Location unavailable`.

Every selected FINISHED fixture opens its `/matches/{id}` details regardless of venue aggregate `illumination_state`, selected filter type, or other fixtures at the venue; only venues with zero selected fixtures are non-clickable. The map's selected round can include completed fixtures and upcoming fixtures; `UPCOMING_ROUND` means highlighted as in the selected round, not playing right now. When selected round has no games, show no-active-fixtures message while keeping stadium geography. Display map tile credit visibly. For temporary tile network failure, retain list/card mode. Do not use any auto-geolocation of user; map location is stadium based.

### 5.8 Personalized "Why this matters" and standings

Impact view includes `My club`, league table with highlighted selected team, nearby rivals and cards for fixtures whose outcomes can change the current points gap or other deterministically supported metric. The feed `GET /impact/relevant` includes HIGH/MEDIUM/LOW plus `UNKNOWN` with caveats (separate **Impact unverified** section, neutral styling); it excludes NONE but NONE fixtures remain accessible via discovery. Optional date/matchday is mutually exclusive; omitting both returns full season. Show low-effort `Recommended for your team` cards based on next favorite-team fixtures and HIGH/MEDIUM/LOW feed, **never** an algorithmic/AI ranking claim. Per match show:

- `Why this matters to [Club]` with explicit scenario outcome and value;

### 6.1 Data model used by components

Use generated types for `MatchSummary`, `ImpactInsight`, `WhatifAnalysis`, `StadiumMapResponse`, `RoomSummary`, `PredictionView`, `UserProfile`. **Status data flow:** `pre_match_room` and `post_match_room` indicate discoverable room existence, not ability to post. **Auth:** credentials transported via HttpOnly cookie. **Phase 1 uses the same-origin Next.js `/api/v1` proxy.** For register/login/logout **and every state-changing request**, the browser sends its ordinary `Origin` header and the backend strictly validates it; do not invent a CSRF header or token. `fetch` should use `credentials:'include'` and explicit JSON content type. In production Secure cookies and same-origin proxy preferred.

**API errors:** normalized client handling by `error.code`. `MATCH_NOT_FINISHED` → no AI composer; `PREDICTION_CLOSED` → lock and refetch; `PREMIUM_REQUIRED` → create-room upsell; `INSUFFICIENT_DATA` → valid HTTP 200 AI analysis verdict only (not a transport error); `RATE_LIMITED` → quota message; `AI_UNAVAILABLE` → preserve draft/retry; provider stale → keep cards and show banner.

### 6.2 Local state vs server state

- `favorite_team_id` guest mirror in localStorage; authenticated server preference is authoritative.
- `selected_season`, `selected_matchday`, `journey_competition_filter`, UI tab and open dialog may reside in URL query params or React state.

Never store a cookie/access token in browser storage.
- Draft text may be held in component state; optional per-thread browser draft must never be shared across accounts. Sign-out clears private caches.
- **HTTP/cache boundary (Appendix A1 normative):** always fetch session-dependent/private responses and all room message/change-feed responses with `cache:'no-store'`; the same-origin `/api/v1` proxy must preserve `Cache-Control: private, no-store` and `Vary: Cookie` where required, including error and mutation responses. Never use Next.js static rendering/ISR or a shared server-side fetch cache for auth, profile, prediction history, private What-if threads, room permissions, room messages, or moderation events. Query caches are partitioned per authenticated identity (explicit guest partition), with private entries removed on logout/login/account switch, plan change, demo-epoch change and session revocation. Never persist the corresponding response payloads in browser storage.

### A1. Transport, authentication, time, errors, and scope

- **Base path:** Every path in A2 is relative to browser-facing `/api/v1`. Next.js rewrites `/api/v1/:path*` to `http://localhost:8000/api/v1/:path*` in local development; browser requests stay same-origin (`http://localhost:3000`). Do not use a cross-origin direct-browser API URL in Phase 1. Backend OpenAPI at `/openapi.json`; health at `/api/v1/health`.
- **Cookies and CSRF:** Browser session is an opaque HttpOnly cookie named `matchline_session`, `Path=/api/v1`, `SameSite=Lax`, `Secure` in HTTPS; no bearer tokens in browser JS. Register/login/logout **and all authenticated mutations** require a valid exact-match `Origin: http://localhost:3000` in development (production uses configured exact frontend origin). Browser POST/PUT/DELETE use `credentials: 'include'`, JSON body, and ordinary browser Origin, with no custom CSRF token/header. Requests lacking a valid Origin are rejected 403 `CSRF_ORIGIN_INVALID`; test clients must supply Origin; trusted CLI integration runs inside app/DB rather than bypassing browser security. `GET` requires no Origin. Never rely on CORS alone.
- **IDs / clocks:** All resource identifiers ending `id`/`_id` (including `client_message_id`) and `Idempotency-Key` use canonical UUID strings. **Exception:** transport/log correlation `error.request_id` is a non-resource opaque string such as `req_01AB`; `source_ref`, `data_version`, cursors, and provider identifiers are also not constrained to UUID. All API timestamps use UTC RFC3339 `YYYY-MM-DDTHH:mm:ssZ`. `season=2026` means 2026–27 season **start year**. Calendar `date=YYYY-MM-DD` is Europe/London civil date; backend applies DST-correct IANA conversion and filters UTC kickoff instants within that local day. Frontend formats match time in Europe/London (with timezone label). Numeric scores/position/coords are genuinely nullable; never invent missing data.
- **Demo clock:** `GET /meta` includes `server_now_utc`, `demo_clock_frozen:boolean`, `mode: 'DEMO'|'LIVE'`, `default_competition:'PL'`, `default_season_start_year:2026`, `demo_epoch:number|null`, `scenario_revision:number|null`, `capabilities:{whatif_sharing:false,events:boolean,live_updates:boolean}`. In DEMO the backend reads a **single injected/fixed clock** (`DEMO_CLOCK_ISO=2026-10-24T12:00:00Z` is used ONLY during first seeding; persisted singleton `app_runtime_state.demo_clock_utc` is authoritative thereafter, re-read on every API request); all prediction cutoffs, room locks, quotas and source-as-of calculations use it. Frontend derives the visible `Demo as of <formatted /meta.server_now_utc>` label **dynamically on every `/meta` refresh** (for example, first baseline `Demo as of 24 Oct 2026, 12:00 UTC`); later scenario transitions must update this display. It **must not** show a real-time ticking countdown against a frozen clock. The management command `python -m app.jobs.demo_transition --scenario baseline|upcoming_live|upcoming_finished` atomically applies scenario-specific **explicit match status + verified synthetic scores/events + standings snapshots + clock** from the seeded manifest. Merely advancing/injecting the clock NEVER promotes SCHEDULED to LIVE or FINISHED, populates scores, or runs settlement. Only the `upcoming_finished` transition runs deterministic prediction settlement for that match. Do not expose any public demo mutation route. In LIVE mode `server_now_utc` is request time; client countdown is informational only; server remains authoritative.
- **Enums:** `MatchStatus=SCHEDULED|LIVE|HALFTIME|FINISHED|POSTPONED|CANCELLED|SUSPENDED|UNKNOWN`; `Illumination=UPCOMING_ROUND|LIVE|COMPLETED|INACTIVE|POSTPONED_OR_CANCELLED|UNKNOWN`; `Plan=FREE|PREMIUM`; `Role=USER|EDITOR`; `RoomKind=PRE_MATCH|POST_MATCH`; `RoomStatus=OPEN|READ_ONLY|HIDDEN`; `Relevance=HIGH|MEDIUM|LOW|NONE|UNKNOWN`; `SourceKind=DEMO_SYNTHETIC|LIVE_PROVIDER`; `PredictionStatus=PENDING|SCORED|VOID`; `Outcome=HOME|DRAW|AWAY`.
- **Errors (all non-2xx JSON responses):** `{ "error": { "code": "STRING_ENUM", "message": "Readable message", "details": {}, "request_id": "req_..." } }`. Codes/status: `UNAUTHENTICATED` 401; `FORBIDDEN`, `PREMIUM_REQUIRED`, `CSRF_ORIGIN_INVALID` 403; `NOT_FOUND` 404 (includes threads owned by another user and any room that is hidden/not yet discoverable, including its messages, changes, and posting paths; no room-existence leak); `PREDICTION_CLOSED`, `ROOM_CLOSED` (includes room creation after PRE_MATCH cutoff or before verified POST_MATCH finish), `MATCH_NOT_FINISHED`, `IDEMPOTENCY_CONFLICT`, `WHATIF_THREAD_BUSY`, `WHATIF_TURN_SUPERSEDED`, `WHATIF_THREAD_LIMIT` 409; `INVALID_INPUT` 422; `RATE_LIMITED` 429 with `details.reset_at` in UTC; `PROVIDER_UNAVAILABLE` 502; `AI_UNAVAILABLE` 503 with `details.client_message_id` and `details.request_state`. `WHATIF_THREAD_LIMIT` is returned only for a **new distinct** user turn beyond the 40-turn thread cap; the error uses the standard envelope with `details.limit=40` and `details.admitted_turns=40`, persists no new turn, and consumes no daily quota. Exact-key replay/retry of an already admitted turn retains its original documented behavior, even if the thread is at the cap. Insufficient evidence or invalid hypothesis in a *successfully processed What-if* is HTTP 200 with a verdict, **not** an HTTP error. Invalid credentials return 401 `UNAUTHENTICATED`. Nullables are explicit, not silently omitted.
- **List envelopes:** Ordinary paginated list is `{items:[...],next_cursor:string|null}` (default limit 20, maximum 100); the room-message list is explicitly `RoomMessagesPage` with additional `sync_after_seq`, and the room change feed is `RoomChangePage` with its own sequence cursor. `GET /teams`, `/competitions`, `/competitions/{code}/matchdays`, `/users/me/badges` and `/matches/{id}/leaderboard` return `{items:[...]}` without cursor. Other lists are newest-first unless otherwise specified; Journey is chronological ascending, standings are position ascending. **Room-message pagination has two explicitly different modes:**
  - **Initial and older-history mode:** `GET /rooms/{id}/messages?limit=N` returns the **latest N public-visible** messages, displayed ascending by `(created_at,id)` within the page. `next_cursor` is an opaque, room-bound **backward** cursor for strictly older messages: `GET ...?cursor=<next_cursor>`. Older pages are also ascending and are prepended; `next_cursor=null` means history exhausted.
  - **Forward catch-up mode:** `GET /rooms/{id}/messages?after_id=<last_seen_message_UUID>&limit=N` returns the **earliest N currently public-visible messages strictly after the referenced stored message's `(created_at,id)`**, ascending. `after_id` may refer to a message since hidden by a moderator; the server resolves its stored sort key but never returns its hidden contents. In this mode `next_cursor` is **always null** (the older-history cursor is not repurposed). The client advances `after_id` to the last ID received and requests again until a page has fewer than `limit` entries (an exactly-full page requires another fetch). A room-mismatched/unknown `after_id` is 422 `INVALID_INPUT`. `cursor` and `after_id` cannot be used together (422). For a busy room, cap pages per UI polling cycle but continue catch-up from the last processed ID next cycle; do not skip IDs. Timestamp ties are broken by UUID, never offsets. After demo-epoch reset/relogin, clear old anchors and fetch the initial window again. A first-load page may be empty; no forward anchor exists until a message is observed.
  - **Public moderation semantics:** only `VISIBLE` and `FLAGGED` rows are returned; a `FLAGGED` report is not automatic hiding. `HIDDEN` rows are excluded entirely from public message responses (**no placeholders or empty-body leaked metadata**) and from `RoomSummary.message_count`. Public `RoomMessage.moderation_state` is therefore only `VISIBLE|FLAGGED`; editors can audit hidden rows through private backend tooling outside these public DTOs. Use the room `/changes` feed to evict a hidden message from **all cached pages**, including loaded older history; never reveal the removed text or author data in placeholder messages. On reload, fetch an initial atomic room snapshot and resume from its returned sequence watermark. Rate-limited polling must retain its forward anchor and reconnect on the next cycle.
  - All reads are deterministic keyset queries; use the same visibility filter for older/forward/initial windows, ensure no overlaps, de-duplicate UUIDs, and render the combined visible timeline in `(created_at,id)` order. Never rely on refetching only the latest page to discover all intervening messages.
  - **Authoritative empty-room and moderation-safe sync (v2.4):** `GET /rooms/{id}/messages` returns `RoomMessagesPage` (the existing page fields **plus `sync_after_seq:number`**). On **initial** fetch the server reads the visible latest window and the per-room committed high-water event sequence in one consistent database snapshot; a returned empty `items=[]` still has a usable sequence. The client retains this initial watermark and uses `GET /rooms/{id}/changes?after_seq=<sequence>&limit=N` for incremental updates, including after an empty initial page; an `after_id` anchor is **not** required. Older-history `cursor`/`after_id` remain supported, but the v2.4 UI uses the change feed as its authoritative live sync and cache-removal mechanism. `RoomChangePage` returns earliest events strictly after `after_seq`, sequence-ascending, with `next_after_seq` equal to the last processed event sequence (or the supplied sequence if none) and `has_more`; the client must continue until `has_more=false`, even across polling cycles. Event seq is room-scoped, monotonically increasing and allocated transactionally on message insert, moderation FLAGGED update, and HIDDEN removal. `UPSERT` contains the **current** public-visible `RoomMessage`, whereas `REMOVE` contains only message UUID and event seq (never content or author metadata); querying an historical `UPSERT` after its message becomes HIDDEN must yield a content-free `REMOVE`, not the formerly visible text. On receipt of `REMOVE`, evict that ID from **all cached history pages**, including far-back pages; on `UPSERT`, insert/update by ID in chronological order. No event-body snapshots from formerly visible but now HIDDEN posts may be exposed. Subsequent paginated older reads must also filter hidden rows. The backend ensures a snapshot/query-bound sequence watermark and does not skip an event if new writes arrive during catch-up; event pages are fetched from the committed per-room sequence while clients continue from the returned `next_after_seq` only, not a wall-clock timestamp. `after_seq` must be an integer >=0 and <= current room sequence; invalid values -> 422. This endpoint complements older-page cursors; it does **not** expose private moderation notes. After demo reset, re-authentication and demo epoch revision, discard room caches and sequence watermarks. Test: empty initial window → 45+ additions at limit=20 → all appear exactly once; hide an old cached message → REMOVE evicts it regardless of loaded page depth; request feed starting at 0 after moderation never leaks old body, retains original event sequence numbers, and paginates across redacted UPSERTs without gaps or altered page-size limits.

- **Provenance:** Every `MatchSummary` has `source.kind`, `is_stale`, `last_synced_at`, `data_version`. Demo fixtures and mock model responses visibly label `DEMO_SYNTHETIC` and `DEMO_AI`. Synthetic score/event/standing examples are **not real historical results**. Map pins only when `coord_verified=true` with independently verified venue coordinates. No real sports-provider permission is assumed.
- **Cross-endpoint HTTP privacy and caching (normative; v2.4):** Every response for session-specific or private resources MUST include `Cache-Control: private, no-store` and `Vary: Cookie`, including `GET /auth/me`, `GET /users/me/profile`, `GET /users/me/badges`, `GET /users/me/predictions`, `GET /matches/{id}/predictions/me`, `GET /users/me/whatif/threads`, `GET /whatif/threads/{thread_id}` and any future Phase 1 private thread history/detail/list route; this includes their 401/403/404/409/429/503 error responses. Register/login/logout (including Set-Cookie or cookie revocation), authenticated mutations and their responses (favorite-team PUT, predictions, private What-if, posting, reporting, room creation) also MUST send `Cache-Control: private, no-store` and `Vary: Cookie`. All `GET /rooms/{id}/messages` and `GET /rooms/{id}/changes` responses, including error/404 cases and room moderation REMOVE event pages, MUST use `Cache-Control: private, no-store` and `Vary: Cookie` even though their visible content is public; never cache visibility-sensitive content. RoomSummary list/detail rules below continue to apply. The backend sends these headers; the same-origin Next.js `/api/v1` proxy MUST preserve them unchanged, MUST not cache these requests or replay them across identities, and the frontend requests these resources with `cache: 'no-store'` (or equivalent). No shared CDN, service-worker persistent cache, ISR, Next.js server fetch cache, or browser storage may cache their bodies. TanStack Query in-memory private/permission/message caches are keyed by the authenticated identity/session (explicit `guest` key), and must be cleared or invalidated on login, logout, user switch, plan/role change, demo epoch change, moderation updates and authorization failure. Backend authorization and visibility always determine truth regardless of stale client state. Public match/venue/competition data may use separate safe caching only when explicitly configured; do not extend that policy to the sensitive routes above.
- **User-dependent room response caching and authorization (normative):** Any GET response containing `RoomSummary` and its contextual `can_post` or `can_create` flags—including `GET /rooms`, `GET /rooms/{id}`, and `GET /matches/{id}/rooms`—MUST set `Cache-Control: private, no-store` and `Vary: Cookie`. Browsers, service workers, the Next.js same-origin proxy, and CDNs MUST NOT serve those personalized permission representations from shared/public caches; the proxy must forward response cache headers unchanged. The backend recomputes flags per request from the authenticated session, plan, room state, and authoritative clock, and enforces writes independently of client flags. Frontend query caches for any contextual room summaries MUST be keyed by authenticated user ID/session identity (use an explicit `guest` partition without a session), and invalidated/cleared on login, logout, account switch, plan/role change, room permission/status update, and demo epoch change. The guest does not inherit a previous premium user's cached create/post permissions. G2/G5 tests switch PREMIUM → FREE → guest → PREMIUM and assert fresh server flags, no shared-cache hit, correct response headers, and backend write denial where applicable.
- **Visibility and room-access uniformity:** Room read routes are public **only for discoverable rooms**. A raw room row with `status=HIDDEN` (including seeded/unactivated POST_MATCH templates) is treated as nonexistent for **all public room-ID routes**, including `GET /rooms/{id}`, `GET /rooms/{id}/messages`, `GET /rooms/{id}/changes`, and (for authenticated callers) `POST /rooms/{id}/messages`: HTTP 404 `NOT_FOUND` with the standard error envelope, no messages/change watermark/count/event metadata, even for an authenticated PREMIUM user. Unauthenticated attempts to `POST /rooms/{id}/messages` receive the standard 401 `UNAUTHENTICATED` without a room existence check; authenticated callers receive identical 404 results for unknown and hidden UUIDs before room-specific write-permission checks. Public indexes/list-by-match exclude hidden rooms. Missing UUID and hidden UUID have indistinguishable responses; validate visibility before content, cursor, change-sequence and write-permission checks. Once a room becomes discoverable, its message reads and changes work under ordinary rules. Editors may use separately authenticated internal moderation tooling, which is not a public API bypass. Room creation `POST /matches/{id}/rooms` is PREMIUM/EDITOR-only; requested PRE_MATCH kind requires SCHEDULED plus backend time strictly before kickoff, requested POST_MATCH kind requires verified FINISHED. Wrong phase/cutoff → 409 `ROOM_CLOSED`; `RoomSummary.can_create` describes the current ability to create another room of the **same kind** for that match, not generic premium entitlement. Room lists never expose hidden templates.
- **Visibility:** Public GETs: matches, Journey, map, standings, teams, room index/detail/messages, match impact and impact feed, leaderboard. Guest selection stays in localStorage only; a logged-in user uses only the server favorite until an explicit consented PUT import (no guest fallback); authenticated favorite-team write/profile/prediction/room posting/AI operations use cookie. Free and Premium can post in OPEN rooms; only Premium (or authorized editor) can create rooms. What-if conversations are private and owned, separate from public rooms.
